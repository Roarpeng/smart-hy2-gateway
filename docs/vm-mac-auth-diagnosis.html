MAC 认证 Wi-Fi 下：宿主正常、虚拟机断网

现场实测于 2026-11-01 · 宿主 Ubuntu / Wi-Fi wlo1 / SSID "room 116" / 策略 whitelist → 判定 on

结案（13:20 已修复）：根因是 /dev/vmnet1 设备节点缺失——虚拟机 14:58 开机，节点 15:02 才出现。vmx 开机打开设备失败后，把「以太网 2」标记为永久断开且不再重试。与 MAC 认证无关。

证据链（vmware.log 原文）：

VNET: MACVNetPortOpenDevice: Ethernet1: can't open vmnet device (No such file or directory)
[msg.vnet.connectvnet] Could not connect 'Ethernet1' to virtual network 'vmnet1'
[msg.device.startdisconnected] Virtual device 'Ethernet1' will start disconnected.

结论一：MAC 认证不会直接封掉 Host-Only 虚拟机。虚拟机的流量经 VMnet1 交给宿主，出 Wi-Fi 时源 MAC 是 wlo1 的 MAC、源 IP 是 10.20.90.45，认证态被完整继承。

结论二：故障不是"代理没接住"，而是"虚拟机的包根本没上来"。vmnet1 收包计数为 0，对 192.168.100.128 的 ARP 一直是 FAILED。

结论三：MAC 认证只通过两条间接路径致断：① 虚拟机网卡被桥到 Wi-Fi，自带 MAC 未认证被 AC 丢弃；② 认证网关的"反共享"按 TTL=63 / 多流特征掐掉宿主转发的直连流量。本次两者均不成立——vmnet0 桥接目标锁在 enp55s0 有线口。

1 · 原理：一条路径，四个断点

虚拟机要上网，包必须穿过四个环节。任一处断，表现都是"虚拟机上不了网"，但处置完全不同——所以先定位，再动手。

3 · 定位流程（按序执行，每步只看一个判据）

STEP 1确认二层有没有包

宿主开一个窗口持续观察收包计数：

watch -n1 "cat /sys/class/net/vmnet1/statistics/rx_packets"

同时在虚拟机内发起三层连通：

ping -c 3 192.168.100.1

判据：计数不增长 → 断点在 ① 二层，跳到 STEP 2。
判据：计数增长但 ping 不通 → 断点在 ④，跳到 STEP 4 的宿主侧检查。

STEP 2核对虚拟机网卡归属（与 MAC 认证直接相关的一步）

VMware → 虚拟机设置 → 网络适配器，逐项核对：

适配器必须是不能是
适配器 1（内网直连）自定义 VMnet0，且 VMnet0 的 Bridged to 锁定 enp55s0Automatic
适配器 2（上网出口）自定义 VMnet1（Host-Only）NAT / 桥接 / 未勾选"启动时连接"
这是 MAC 认证场景下唯一的直接致死路径：VMnet0 若设为 Automatic，VMware 可能把桥接落到 wlo1。此时虚拟机以自己的 MAC 直接出现在 Wi-Fi 上，该 MAC 未在任何认证系统中登记 → 帧被 AC 丢弃。若虚拟机又把默认路由放到这块网卡上，整机断网；而宿主毫无异常，症状完全吻合。

判据：两块网卡均须为 Custom 且显式指定 VMnet0 / VMnet1，桥接目标必须是物理有线口（当前 enp55s0，状态 DOWN，插线前该口不通属正常）。

STEP 3核对该虚拟机的地址与默认路由
# Linux
ip -4 addr show
ip route

# Windows（管理员 PowerShell）
ipconfig /all
route print -4

预期：存在default via 192.168.100.1（metric 100）；另一块网卡即便有地址也不抢默认路由。
判据：默认路由指向物理网段（如 10.20.90.1）→ 该虚拟机的流量绕开了网关，直接改回 192.168.100.1。

STEP 4确认包进了隧道，而非漏成直连

虚拟机内执行：

curl -s ifconfig.me; echo

预期：返回节点出口 IP（当前节点 66.154.125.150）。
返回 10.20.90.45：流量未命中 TProxy，走了直连——检查宿主 proxy-switch.sh status 与 hy2_cn 命中情况。
超时：包到了但没人接——在宿主看 sing-box 日志是否出现 inbound from 192.168.100.x：

docker logs --tail 200 hy2-gateway | grep '192.168.100.'
STEP 5区分"被反共享掐断"与"隧道故障"

虚拟机内分别测国内与国际：

curl -s -o /dev/null -w 'cn=%{http_code}\n' https://www.baidu.com
curl -s -o /dev/null -w 'intl=%{http_code}\n' https://www.google.com
现象含义
两项都通链路正常，问题已解决
intl 通、cn 不通典型反共享：国内 IP 命中 hy2_cn 被内核放行 → MASQUERADE 直连 → TTL=63，被 AC 判定多设备共享
两项都不通，且宿主同时掉线账号已被反共享策略踢下线，需重新认证
两项都不通，宿主正常非反共享，回到 STEP 1—4 查转发链路

4 · 处置矩阵

已定位原因处置动作验证
二层：网卡归属错 / 未连接 / 桥到 Wi-Fi VMware 中改为 Custom VMnet0（桥接锁 enp55s0）+ Custom VMnet1；勾选"启动时连接"；必要时先删后按序重加 vmnet1 RX 计数随 ping 增长；ip neigh 由 FAILED 转 REACHABLE
路由：默认网关缺失或被抢占 网关设为 192.168.100.1，metric 100；桥接网卡 metric 调高（200） ip route 默认项指向 vmnet1
反共享：TTL 特征被识别 宿主统一改写转发流量 TTL（需 xt_HL，本机已具备）：
iptables -t mangle -A POSTROUTING -s 192.168.100.0/24 -o wlo1 -j TTL --ttl-set 64		 VM 内国内站点恢复；iptables -t mangle -S POSTROUTING | grep TTL
反共享：仍被识别（多流 / 指纹） 让虚拟机全部流量走隧道（隧道流量由 sing-box 重新发起，TTL=64，与宿主流量无差别）：移除 HY2_PRE 的 hy2_cn RETURN 规则，或在控制台将通道策略设为 always_proxy 并观察 VM 内 curl ifconfig.me 恒为节点 IP
转发：包到了没人接 核对 ip_forward=1、ip rule fwmark 1、sing-box 监听 [::]:12345；用 proxy-switch.sh on 重建规则 sing-box 日志出现 inbound from 192.168.100.x

为什么 MAC 认证不影响 Host-Only 方案

认证发生在 Wi-Fi 关联/关联后的 ACL 上，认的是发出该帧的 MAC。虚拟机流量在宿主内核被 TPROXY 接管或 MASQUERADE 重写，出 Wi-Fi 时源 MAC 恒为 wlo1 的 MAC。

因此"虚拟机用宿主的认证态"是设计本身的正常表现，不需要也不应该给虚拟机单独认证。

为什么反共享偏偏掐虚拟机

隧道流量由 sing-box 在宿主上重新发起，TTL、IPID、TCP 特征与宿主自己的流量一致。

而 hy2_cn 放行的国内流量走内核转发，TTL 被减 1 变成 63——这正是 AC 判定"下游还有一台设备"的经典特征。

5 · 风险与回滚

操作前：本次只做只读检查与规则新增，未改动现有配置。若执行 TTL 改写，先确认命令中的出口网卡名是 wlo1（换网络环境后网卡名可能变化）。
  • TTL 改写的回滚：iptables -t mangle -D POSTROUTING -s 192.168.100.0/24 -o wlo1 -j TTL --ttl-set 64
  • 规则整体回滚：sudo /usr/local/bin/proxy-switch.sh off 清除 TProxy 并恢复直连
  • 风险：反共享策略若已触发账号封禁，改 TTL 不会立即恢复，需在认证页重新登录；频繁触发可能导致账号被限速。
  • 不要为"让虚拟机通过认证"而克隆宿主 MAC 到虚拟机网卡——同网段出现重复 MAC 会造成 AP 侧 ARP 表震荡，宿主与虚拟机同时掉线。

6 · 一个已确认的工具缺陷（顺带记录）

在容器内直接执行 proxy-switch.sh status 会误报。原因是脚本默认 STATE_FILE=/opt/hy2-gateway/data/gateway_state.json，而容器只挂载了 /data；读取失败后回落到内置默认网卡名 wlp2s0 / enp3s0，于是把实际存在的规则报成 [无]。

宿主侧脚本与后端调用均通过 proxy_switch_env() 显式传入正确路径与网卡名，不影响实际转发，仅影响容内手工排障时的读数。核验时请以 iptables -t mangle -S 的实际输出为准。
